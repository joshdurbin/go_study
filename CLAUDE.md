## File conventions

Every lesson is a self-contained `package main` with its own `func main()`. To avoid `go build ./...` errors from N mains in one directory, **every lesson file starts with `//go:build ignore`**. This excludes them from package builds but `go run <file.go>` (which the server uses) still works because explicit-file `go run` bypasses build tags.

### Per-lesson file set

| Suffix              | Required for                | Purpose |
|---------------------|------------------------------|---------|
| `<topic>.go`        | basics, patterns, interview | Reference solution / full lesson source. Must compile and run. |
| `<topic>.md`        | basics, patterns, interview | Markdown notes (basics/patterns) or problem statement (interview). Rendered via Marked.js. |
| `<topic>.steps.md`  | interview only              | Progressive hints. Split on `## Hint N` headings. Code fences `` ```go `` are rendered with syntax highlighting. |
| `<topic>.starter.go`| interview only              | Editor scaffold — function signatures with `// TODO: implement` bodies + a `main()` with example inputs/outputs as comments. Excluded from sidebar. |

For basics/patterns, the `.go` source IS the editor starter (no `.starter.go` needed).

### Naming and ordering

- Numeric prefix on `.go`/`.md` files (e.g., `13_goroutines.go`) controls **display order**. The prefix is stripped by `prettify()` for the sidebar label.
- Block directories use `blockN_<name>` (e.g., `block5_trees_graphs`). The same `prettify()` strips `block` and the number.
- Warmup tiers use `1_easy`, `2_medium`, `3_hard` to force display order — alphabetical would put hard before medium.

### Hint format (`.steps.md`)

Tier-scaled hint counts, tight narrative, progressive code:

| Tier              | Hints | Shape |
|-------------------|-------|-------|
| Easy              | 2     | skeleton → near-complete |
| Medium            | 3     | skeleton → core logic → refinement/pitfall |
| Hard              | 4     | setup → recurrence → main loop → finishing touches |

Each hint = 1–3 sentences of prose + a 3–10 line fenced code block. Last hint should be ~80% of the solution but not identical to it.

```markdown
## Hint 1
Tight nudge in 1-2 sentences.

​```go
// minimal code skeleton
​```

## Hint 2
Next step.

​```go
// adds the core logic
​```
```

## How the server works

- `cobra` CLI; `viper` for config. Two commands: `serve` and `version`. Migrations run automatically on startup — no manual `migrate` command.
- `pure-Go modernc.org/sqlite` + embedded goose migrations + sqlc-generated queries.
- Section loader scans on EVERY `GET /` (dynamic — no restart needed when adding files).
- `safePath()` validates against fixed `sectionDirs` (basics, patterns, interview_study, interview_qa) — adding new content doesn't require updating safety checks.
- `/api/run` writes the editor `code` to a temp file and runs it with a 15s timeout. The 15s timeout is also the hard ceiling.
- WebSocket `/ws` carries `focus`/`blur`/`tick` frames for time tracking.
- Anonymous per-browser session cookie (`study_session`); every event keyed by `session_id + lesson_path + section`.

## Build / run

```bash
make build              # go build -o go_study .
make run                # builds + serves on :8080 (auto-migrates)
make sqlc               # regenerate internal/db/store from queries.sql
go build ./...          # whole-module build (passes because lesson files have //go:build ignore)
```

## When adding content

Use the relevant slash command — they encode the conventions:

- **`/add-basic`** — new fundamentals lesson under `basics/`
- **`/add-pattern`** — new design pattern under `patterns/`
- **`/add-interview-problem`** — new algorithm problem under `interview_study/<block>/...`

Interview Q&A entries (`interview_qa/`) follow the basics file convention (one numbered `.go` demo + matching `.md`), but the `.md` uses a Q&A structure (`## The question`, `## The answer`, `## The gotcha`, `## In code`, `## Related`) rather than the basics lesson structure.

Each skill knows the file set, the hint difficulty scaling, the markdown structure, and where to place the new content. They keep the corpus consistent without you having to re-derive the conventions every time.

The web app dynamically rescans the lesson tree on every page load, so dropping new files into the right directory makes them immediately visible — no restart needed.
